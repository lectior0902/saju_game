# 배포 가이드

사주 루트는 서버가 필요 없는 **정적 웹앱**이에요. 계산과 저장이 모두 방문자의 브라우저 안에서 끝나서, 파일만 올릴 곳이 있으면 배포가 끝나요. 이 문서는 (1) 가장 빠른 배포 경로, (2) 정식으로 공개하기 전 점검 항목, (3) 서버가 필요해지는 시점과 그때의 구조를 설명해요.

서비스별 무료 한도와 정책은 자주 바뀌어요. 가입하기 전에 각 서비스의 공식 문서에서 현재 조건을 확인하세요.

## 1. 지금 상태

| 위치 | 상태 |
|---|---|
| claude.ai 아티팩트 | 비공개 링크. 공유 메뉴에서 열어 준 사람만 볼 수 있어요. 시험용으로 적당해요. |
| 이 프로젝트 | 독립 배포가 가능한 구조예요. `npm run build`로 `dist/`가 만들어져요. |

## 2. 가장 빠른 배포 3가지

모두 빌드 명령은 `npm run build`, 배포 폴더는 `dist`예요.

### A. 드래그 앤 드롭 (5분, 계정 필요)
1. `npm install` 후 `npm run build`
2. 생성된 `dist` 폴더를 Netlify Drop 같은 정적 호스팅의 드래그 영역에 올려요.
3. 발급된 주소로 바로 접속돼요.

코드 관리 없이 한 번 올려 보는 용도예요. 수정할 때마다 다시 올려야 해요.

### B. GitHub Pages (자동 배포, 추천)
이미 `.github/workflows/deploy.yml`이 들어 있어요. main에 푸시하면 테스트, 빌드, 배포가 자동으로 돌아요.
1. GitHub에 저장소를 만들고 이 폴더를 올려요.
   ```
   git init && git add . && git commit -m "first commit"
   git branch -M main
   git remote add origin https://github.com/<아이디>/<저장소>.git
   git push -u origin main
   ```
2. 저장소 Settings → Pages → Source를 **GitHub Actions**로 바꿔요.
3. Actions 탭에서 `deploy` 실행이 초록색이 되면 `https://<아이디>.github.io/<저장소>/`에서 열려요.

`vite.config.js`의 `base: "./"` 덕분에 하위 경로에서도 별도 설정 없이 동작해요. 비공개 저장소에서 Pages를 쓸 수 있는지는 요금제에 따라 달라서 확인이 필요해요.

### C. Netlify, Vercel, Cloudflare Pages (저장소 연결)
저장소를 연결하고 빌드 명령 `npm run build`, 출력 폴더 `dist`를 입력해요. `netlify.toml`에는 Netlify용 설정과 기본 보안 헤더가 들어 있어요. 푸시할 때마다 자동으로 배포되고, 브랜치별 미리보기 주소도 받을 수 있어요.

### 도메인 연결
도메인을 사서 호스팅 서비스의 Custom domain 메뉴에 등록하고, 안내하는 DNS 레코드(CNAME 또는 A)를 도메인 업체에 입력해요. HTTPS 인증서는 대부분 자동 발급돼요. HTTPS가 아니면 PWA 설치와 일부 브라우저 기능이 막혀요.

## 4. 만세력 정확도 높이기

지금은 절기를 날짜로만 근사해서 입춘, 경칩 같은 절기 당일 전후 하루가 틀릴 수 있어요. 정식으로 내놓을 때는 분 단위 절기 시각이 필요해요.

1. 신뢰할 수 있는 데이터를 정해요. 후보는 오픈소스 만세력 라이브러리, 또는 한국천문연구원이 공공데이터포털로 제공하는 24절기 정보예요. 시각까지 제공하는지, 사용 조건이 무엇인지는 직접 확인해야 해요.
2. `src/core/data.js`의 `TERMS`를 연도별 시각 표로 바꾸고 `pillars()`의 월·년 경계 판정을 시각 비교로 바꿔요.
3. 검증은 지금 구조를 그대로 쓰면 돼요. `reference/make_fixture.py`가 만드는 픽스처를 **신뢰하는 만세력의 출력**으로 바꾸고 `npm test`의 대조 테스트(`tests/saju.test.mjs`)를 통과시키면, 코드를 고쳐도 결과가 흔들리지 않아요.

## 5. 개인정보

생년월일시는 다른 정보와 결합하면 개인을 알아볼 수 있는 정보로 다뤄질 수 있어요. 지금은 이 값이 방문자의 기기 밖으로 나가지 않아요. 아래를 유지하면 수집과 보관에 따른 부담이 작아요.

- 생년월일시를 서버로 보내지 않아요.
- 브라우저에 저장하는 것은 엔딩 도감(어떤 엔딩을 봤는지)뿐이에요.
- 분석 도구를 붙일 때는 이름, 생년월일시 같은 입력값이 이벤트에 실리지 않게 해요. 쿠키 없이 집계만 하는 도구를 고르세요.

서버에 입력값이나 결과를 저장하는 기능(계정, 기록 공유, 랭킹)을 넣는 순간 개인정보 처리방침, 수집 항목 고지, 동의 절차가 필요할 수 있어요. 저는 법률 자문을 할 수 없어서, 그 단계에서는 전문가 확인을 권해요. 미성년자가 이용할 수 있는 서비스라면 그 점도 같이 확인하세요.

권장 보안 헤더(호스팅 설정에서 지정)는 아래와 같아요. 적용한 뒤 브라우저 개발자 도구의 콘솔에서 차단된 항목이 없는지 확인하세요.
```
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; manifest-src 'self'; base-uri 'none'; form-action 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
```
스타일 속성을 코드로 지정하는 부분이 있어서 `style-src`에 `'unsafe-inline'`이 필요해요. 스크립트는 외부 파일이라 `script-src 'self'`로 막을 수 있어요.

## 6. 앱처럼 설치하게 하려면

| 방법 | 설명 | 비용·난이도 |
|---|---|---|
| PWA | 이미 매니페스트와 아이콘이 있어요. HTTPS로 배포하면 브라우저 메뉴의 "홈 화면에 추가"로 설치돼요. 오프라인 실행까지 하려면 서비스 워커를 추가해요(`vite-plugin-pwa` 등). | 낮음 |
| 앱 스토어 | Capacitor 같은 도구로 웹앱을 앱 껍데기에 담아 올릴 수 있어요. 스토어 심사 기준상 단순히 웹을 감싼 앱은 추가 기능을 요구받을 수 있어서, 푸시 알림이나 기기 기능 같은 앱다운 요소를 같이 계획하세요. 개발자 계정 비용이 들어요. | 중간 |

## 7. 성능 개선

- **한글 폰트 용량**: 나눔명조 800이 약 0.7MB, 고딕 A1이 두 굵기 합쳐 약 0.5MB예요. 화면에 쓰는 글자는 몇백 자뿐이라, 쓰는 글자만 남긴 서브셋 폰트로 바꾸면 크게 줄어요. `fonttools`의 `pyftsubset`으로 만들 수 있어요. 글자는 `src/` 안의 한글을 모아서 뽑으면 돼요. 텍스트를 바꿀 때마다 서브셋을 다시 만들어야 하는 점을 감안하세요.
- **캐시**: Vite가 파일 이름에 해시를 붙이니, 호스팅에서 `assets/`에 긴 캐시를 주고 `index.html`만 짧게 두세요.
- **측정**: 배포 후 실제 폰, 느린 네트워크 조건에서 첫 화면까지 걸리는 시간을 재세요.

## 8. 서버가 필요해지는 시점

아래 기능을 넣으려면 서버(또는 서버리스 함수와 DB)가 필요해요.

| 기능 | 필요한 것 | 저장하는 값(권장) |
|---|---|---|
| 엔딩 통계("내 결과는 상위 몇 %") | 집계 API와 DB | 변주 키, 엔딩 키, 환경 키, 총 성취. **생년월일시와 개인 식별자는 저장하지 않아요** |
| 결과 공유 링크 | 결과 저장소 또는 링크에 값을 담는 방식 | 링크에 변주·엔딩·환경 키를 담으면 서버 없이도 가능해요 |
| 계정과 기록 동기화 | 인증, DB | 이 단계부터 개인정보 처리 체계가 필요해요 |
| 랭킹 | 점수 검증, 부정 방지 | 미니게임은 클라이언트에서 돌아서 점수 조작이 쉬워요. 순위의 신뢰도를 어느 정도로 둘지 먼저 정하세요 |

서버를 붙이더라도 게임 규칙(`src/core`)은 DOM에 의존하지 않는 순수 함수라서, 같은 코드를 서버에서 불러 결과를 다시 계산해 검증할 수 있어요.

## 9. 운영 체크

- **오류 확인**: 처음에는 호스팅의 접속 통계와 브라우저 콘솔로 충분해요. 사용자가 늘면 오류 수집 도구를 고려하세요.
- **버전 관리**: 규칙을 바꿀 때 `package.json`의 버전과 `docs/design.md`를 같이 올리고 git 태그를 달아 두면, 나중에 "이 엔딩은 어느 버전 규칙이었나"를 추적할 수 있어요.
- **회귀 방지**: 규칙 숫자를 바꾸면 `npm run sim`으로 엔딩 분포를 먼저 확인하세요. `npm test`가 9개 엔딩의 도달 가능성과 환경 격차의 범위를 검사해요.
- **연구용으로 쓸 때**: 플레이 로그를 모으려면 연구윤리 심의와 참여자 동의가 필요할 수 있어요. 이 프로젝트에는 로그 수집 기능이 없어요.

## 10. 배포 직전 순서 요약

1. `npm install`
2. `npm test` (61개 테스트)
3. `npm run build` 후 `npm run preview`로 로컬에서 확인
4. 3절 점검표에서 "정확도"와 "개인정보" 항목 확인
5. 2절 방법 중 하나로 배포
6. 실제 폰에서 미니게임 3종을 한 번씩 해 보기
